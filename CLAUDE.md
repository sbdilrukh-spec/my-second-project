# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Веб-приложение расчёта рассеивания загрязняющих веществ в атмосфере по методике ОНД-86 для инженеров-экологов Узбекистана. Заменяет связку «Радуга» + CorelDRAW: расчёт, интерактивная карта (heatmap / сетка ОНД; изолинии убраны — не используются) и экспорт отчётов в одном месте. Интерфейс двуязычный (ru/uz, словари в `frontend/src/i18n.js`). Подробное ТЗ и контекст предметной области — в `docs/DOCUMENTATION.md` и `docs/ECOSYSTEM.md`.

## Команды

```bash
# Всё сразу (Windows): бэкенд + фронтенд + браузер
start.bat

# Бэкенд отдельно (FastAPI, порт 8000; venv уже создан в backend/venv)
cd backend && venv\Scripts\activate && python run.py

# Фронтенд отдельно (Vite dev-сервер, порт 5173, /api проксируется на 8000)
cd frontend && npm run dev

# Проверка сборки фронтенда (тестов и линтера в проекте нет)
cd frontend && npx vite build

# Быстрая проверка расчётного ядра без запуска сервера
backend/venv/Scripts/python.exe -c "from app.ond86 import ..."  # запускать из backend/, либо с PYTHONPATH=backend
```

**Деплой:** push в `main` → Render автоматически собирает Docker-образ и обновляет сайт (несколько минут). Локальные изменения на сайт не попадают, пока не запушены. Коммитить/пушить только по просьбе пользователя — он сначала проверяет локально.

## Архитектура

Монорепо из двух частей, в проде — один Docker-образ: FastAPI отдаёт и API, и собранную статику фронтенда.

**Frontend** (`frontend/src/`): React 18 + Vite + react-leaflet. Всё состояние проекта живёт в `App.jsx` (sources, meteo, grid, enterprise, справочник веществ) — БД нет. Кнопка «Рассчитать» отправляет весь проект в `POST /api/calculate`, ответ целиком заменяет `result`. Карта `MapView.jsx` рисует поле на canvas-оверлеях поверх Leaflet (heatmap / сетка с числами).

**Backend** (`backend/app/`): FastAPI, полностью stateless для расчётов — все данные вещества приходят в теле запроса, справочник для расчёта не нужен.
- `ond86.py` — расчётное ядро, строго по ОНД-86 (2.1–2.30): Cm/xm/um по веткам горячий/холодный, s1 с поправкой (2.24) для низких источников, s2 (2.28), r/p (2.29–2.30), F влияет на Cm/xm. В каждой точке, как в «Радуге», перебор направлений (10°, затем уточнение 1°) и скоростей ветра 0,5…U* (затем уточнение 0,1 м/с) — запоминаются опасные HB и U (`points[].d/u`). Внутренний цикл — numba (`ond86_kernel.py`, прогрев при старте сервера), без numba — тот же перебор на numpy. Сверено с распечаткой «Радуги» (QH ±2%). `compute_per_substance` считает все вещества на ОБЩЕЙ сетке (центроид всех источников проекта) — иначе PNG разных веществ не совпадают с подложкой. Площадной источник — N×N подысточников. `_SubstanceSourceProxy` подсовывает выброс одного вещества — новые поля `SourceInput`, влияющие на расчёт, надо копировать и в прокси.
- Номер источника (`number`, задаёт пользователь: 0001, 6001…) идёт в таблицы 7/8/13, на маркеры и в карточки; правило подстановки (поле `number` → число в начале названия «№154 …» → порядковый) — `source_number()` в ond86.py и `sourceNumber.js` на фронте (должны совпадать).
- `raduga_docx.py` — таблицы 1, 7, 8, 12, 13 в Word, строки символ в символ как распечатка «Радуги». HB в них — конвенция «Радуги»: 270° − метеорологическое направление.
- `models.py` — `SourceInput` несёт и новую модель (`emissions: [EmissionEntry]`), и старые плоские поля (substance/emission_gs на верхнем уровне) для обратной совместимости; `get_emissions()` мигрирует на лету. `EmissionEntry.get_emission_gs()` падает обратно на т/год, если г/с не задан.
- `main.py` — все эндпоинты; экспорты PDF/PNG/Excel принимают `precomputed_result` от фронта, чтобы не пересчитывать. Опциональная парольная защита: env `APP_PASSWORD`/`APP_USERNAME` (задаются в дашборде Render); `/api/health` всегда открыт, иначе не пройдёт health-check.
- `import_sources.py` — импорт xlsx/CSV. Шаблон = лист «2-бўлим» ПЗВОС (колонки A–T по позициям, + код вещества и широта/долгота справа, строка «Начало координат» сверху): X1/Y1 карты-схемы переводятся в lat/lon от начала, X2/Y2+ширина → площадной источник, узбекские названия веществ → коды справочника (`SUBSTANCE_ALIASES`). Плоская таблица с однострочной шапкой тоже понимается. Координаты — десятичные или Г-М-С. Параметры трубы протягиваются из строки выше только в пределах того же источника.

**Соглашение о типе источника:** фронт хранит тип в поле `type` ("stack"/"area"), бэкенд ждёт `source_type` — маппинг в `toBackendSources()` в App.jsx. При переключении на "area" и при загрузке проекта размеры площадки материализуются в данные (`handleSourceChange`, `migrateSource`) — без них бэкенд молча считает источник точечным.

## Вещества — три места хранения (важно!)

1. Встроенный справочник `backend/app/substances.py` (~170 позиций) + серверные `custom_substances.json`/`hidden_substances.json` рядом с кодом — **на Render эти JSON эфемерны и стираются при каждом деплое**.
2. localStorage браузера (`customSubstances`) — вещества, добавленные через форму в карточке источника.
3. Файл проекта JSON — объект вещества встроен в каждый emission + массив `customSubstances`; это единственный надёжный носитель. При загрузке проекта фронт «усыновляет» незнакомые вещества в localStorage (эффект в App.jsx).

Расчёту серверный справочник не нужен; пропажа веществ из выпадающих списков после деплоя — следствие п.1.

## Производительность фронтенда

Проекты бывают на сотни источников; полная карточка источника — это сотни DOM-узлов (селект веществ ~170 опций на каждый выброс). Поэтому: карточки свёрнуты при >15 источниках и рендерятся порциями по 30 с поиском; таблица — порциями по 100; маркеры карты мемоизированы поштучно; localStorage-автосейв парсится один раз (ленивый useState). `SourceForm` обёрнут в `React.memo` — обработчики из App должны оставаться стабильными (useCallback с функциональными setState). Не ломать эти инварианты при правках App.jsx.

**Бэкенд-экспорты:** файлы отдаются целиком через `Response(content=...)` — не `StreamingResponse(io.BytesIO(...))`, который режет двоичный файл по `
` на десятки тысяч кусков. Числа в ячейках PNG-сетки ОНД рисуются PIL поверх растра (`_save_with_cell_labels`), а не `ax.text` — тысячи Text-объектов matplotlib были главной задержкой. Word собирается прямым XML, не `doc.add_paragraph()` (тот медленный на тысячах строк).

## Особенности методики (не баги)

- Сетка привязана к центроиду всех источников: правка/удаление источника смещает все узлы, значения в ячейках меняются, пики «переезжают». Это свежий честный расчёт, а не след старого. Между веществами одного расчёта сетка общая.
- Класс устойчивости в расчёте не участвует (ОНД-86 его не использует); скорость ветра в метеоданных — U* (верхняя граница перебора скоростей).
- Низкие источники (H≈2 м) дают гиперлокальный пик (Xm ~20–30 м): на сетке 500 м это одинокая «раскалённая» ячейка среди почти нулевых, а максимум поля сильно зависит от шага сетки.
- Максимальные концентрации по ОНД-86 считаются при средней максимальной температуре самого жаркого месяца; среднегодовая температура занижает результат (особенно для источников с малым перегревом ΔT — там переключается «холодная» ветвь формулы).
- В таблице источников Cm выводится в мг/м³, поле на карте — в долях ПДК; сравнивать напрямую нельзя.

## Рабочий процесс пользователя

Отчётные карты собираются вручную в CorelDRAW из прозрачных PNG (эндпоинт экспорта PNG), PDF-отчёт — вспомогательный. Формат таблиц PDF выверен под «Радугу» — менять структуру таблиц 1/7/8/13 только по явной просьбе.
